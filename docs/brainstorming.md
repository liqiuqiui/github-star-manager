# GitHub Star Manager — 功能迭代方向

> 创建日期：2026-06-06
> 基于竞品调研和用户痛点分析，梳理插件未来的功能演进路径。

---

## 一、数据洞察 & 分析

### 1.1 Star 全景仪表盘

为用户提供一份关于自己 Star 行为的"数据画像"：

- **语言分布**：饼图/柱状图展示 Star 仓库的语言构成（JavaScript 40%、Rust 15% …），让用户对自己的技术偏好有量化认知
- **时间趋势**：按月/季度统计 Star 数量变化，识别哪段时间 Star 最密集（可能对应新项目调研期）
- **Star 数分布**：你 Star 的仓库中，多少是 1k+ Star 的热门项目 vs 小众精品
- **Owner 分布**：你 Star 最多的组织/个人是谁（比如你 Star 了 30 个 `vercel` 的项目）

**实现思路**：数据全部来自本地缓存（IndexedDB），不需要额外 API 调用。前端用 Chart.js 或 Recharts 渲染图表。

**优先级**：⭐⭐⭐ 高价值、中等成本

---

### 1.2 仓库健康度检测

标记出用户 Star 列表中需要关注的仓库状态：

- **已归档（Archived）**：仓库被 owner 标记为 archived
- **长期不活跃**：最近一次 commit 超过 1 年
- **已删除/私有化**：曾经 Star 过但现在 404 了
- **License 变更**：仓库 License 从宽松变为限制型

提供"一键清理"入口，批量取消 Star 这些不健康的仓库。

**实现思路**：在增量同步时额外请求每个仓库的 `isArchived`、`pushedAt` 等字段（GraphQL 一次请求 100 个，开销可控）。对已删除的仓库，记录下来标记为"无法访问"。

**优先级**：⭐⭐⭐ 高价值、低开发成本。直接命中用户痛点（"5000 个 Star 变成信息垃圾堆"）。

---

### 1.3 Star 历史趋势

内嵌 Star 增长曲线，鼠标悬停仓库卡片即可查看：

- 展示仓库从创建到现在的 Star 数增长曲线
- 标注关键节点（比如突然暴涨的时间点，可能对应被大 V 推荐）
- 帮助用户判断一个项目是在上升期还是已过气

**实现思路**：可复用 star-history.com 的 API 或自行计算（按月采样 Star 数）。数据量大时可延迟加载，只在用户主动展开时请求。

**优先级**：⭐⭐ 高价值、中等成本。竞品 Remu 有此功能且用户反馈好。

---

## 二、智能发现 & 推荐

### 2.1 相关仓库推荐

基于用户已 Star 的仓库，推荐可能感兴趣的新项目：

- 分析已有 Star 的 `topics`、`language`、`owner`，生成用户兴趣画像
- 从 GitHub Trending 或 Search API 中筛选匹配的仓库
- 标注推荐理由（"因为你 Star 了 X 和 Y"）

**实现思路**：本地计算兴趣权重，结合 GitHub Search API `q=topic:xxx+language:yyy` 获取候选仓库。可在增量同步时静默更新推荐列表。

**优先级**：⭐⭐ 中等价值、中等成本。增加插件的"发现"属性，提升打开频率。

---

### 2.2 关注用户的 Star 动态

分析你 follow 的用户最近 Star 了什么：

- 拉取 follow 列表中用户的公开 Star 活动
- 按时间倒序展示，帮助用户发现"朋友圈"里的新动向
- 一键 Star + 分类

**实现思路**：GitHub API 支持查询指定用户的 Star 活动（需要关注用户设为公开）。可作为"动态 Feed"面板。

**优先级**：⭐ 中等价值、中等成本。社交属性强，但依赖其他用户设置公开 Star。

---

### 2.3 Trending 对比面板

内嵌 GitHub Trending，与已有 Star 交叉对比：

- 展示当日/本周/本月 Trending 仓库
- 自动标记"你已经 Star 过的"和"你可能感兴趣的"
- 支持按语言筛选 Trending

**实现思路**：可调用开源的 GitHub Trending API（如 `https://api.gitterapp.com/repositories` 或自建轻量爬虫）。

**优先级**：⭐⭐ 高价值、中等成本。解决"发现好项目"的需求，增加插件使用场景。

---

## 三、自动化 & 工作流

### 3.1 自动标签规则引擎

用户设置规则，新增 Star 自动分类，无需手动操作：

- 规则示例：
  - `topic 包含 "rust"` → 自动打标签「系统编程」
  - `language == "TypeScript" && owner == "vercel"` → 打标签「前端框架」
  - `star_count > 5000` → 打标签「热门项目」
- 规则支持 AND/OR 组合
- 规则可对存量 Star 批量执行（首次设置时一次性分类所有已有 Star）

**实现思路**：规则存储在 `chrome.storage.sync`，Star 同步时逐条匹配。可用简单的表达式引擎或 JSON DSL。

**优先级**：⭐⭐⭐ 高价值、低开发成本。竞品完全没有此功能，是强差异化卖点。

---

### 3.2 Star 后即时分类

Star 一个仓库后，立即弹出轻量面板：

- 显示仓库名称和描述
- 快速选择要加入的 Star List
- 快速打本地标签
- 支持"稍后分类"（进入"未分类"队列）

**实现思路**：Content Script 监听 GitHub 页面上的 Star 按钮点击事件，或者通过 Background Script 监听 Star API 调用。弹出 Popover 或小型浮层。

**优先级**：⭐⭐⭐ 高价值、低开发成本。解决"Star 完就忘"的核心痛点。

---

### 3.3 定期清理提醒

设定周期性提醒，引导用户整理 Star：

- 可配置频率：每周 / 每月 / 每季度
- 提醒内容：
  - 有多少新增未分类的 Star
  - 有哪些仓库已归档或长期不活跃
  - "你已经 30 天没整理 Star 了，当前有 47 个未分类"
- 提醒方式：浏览器通知 badge 或插件内横幅

**实现思路**：Background Script 使用 `chrome.alarms` API 设置定时任务，触发时检查同步状态。

**优先级**：⭐⭐ 中等价值、低开发成本。轻量但有效。

---

## 四、数据可移植性

### 4.1 导入 / 导出

支持多种格式的数据互操作：

- **导出格式**：
  - JSON（完整数据，含标签、列表、笔记）
  - CSV（适合 Excel / Google Sheets 查看）
  - Markdown（生成 Awesome List 风格的文档）
  - OPML（RSS 阅读器兼容）
- **导入来源**：
  - 从 JSON 备份恢复
  - 从其他工具（Astral、Remu）迁移
  - 从 GitHub Star Lists 直接导入为本地标签

**实现思路**：纯前端操作，读写 IndexedDB + Blob 生成文件下载。导入时做数据校验和冲突处理。

**优先级**：⭐⭐⭐ 高价值、低开发成本。用户痛点中"数据锁定"是重要顾虑。

---

### 4.2 Star Lists ↔ 本地标签双向同步

打通 GitHub Star Lists 和本地标签两套系统：

- **Lists → 标签**：一键把每个 Star List 的内容同步为对应的本地标签
- **标签 → Lists**：选择性地把本地标签导出为 GitHub Star List（需注意 32 个上限）
- **增量同步**：只同步变更部分，而非全量覆盖

**实现思路**：以 `full_name` 为 key 做关联映射。需要注意 Lists 有 32 个上限的限制，标签转 Lists 时要提示用户。

**优先级**：⭐⭐ 中等价值、中等成本。强化双模式分类的统一性。

---

## 五、GitHub 页面增强（Content Script）

### 5.1 GitHub 页面内注入标签

在 GitHub 原生页面上直接展示和编辑本地标签：

- **Star 列表页**（`github.com/{user}?tab=stars`）：在每个仓库旁边显示已分配的标签，支持直接编辑
- **仓库详情页**（`github.com/{owner}/{repo}`）：显示该仓库在你体系中的标签和所属列表
- **标签样式**：与 GitHub 原生 UI 风格一致的小 badge

**实现思路**：Content Script 注入 DOM，读取本地标签数据渲染 badge。需要 MutationObserver 监听 GitHub SPA 路由切换。

**优先级**：⭐⭐⭐ 高价值、中等成本。直接在用户最常停留的页面提供价值，减少"打开插件"的动作。

---

### 5.2 仓库页面快速操作按钮

在任何 GitHub 仓库页面注入一个操作面板：

- 快速 Star / Unstar
- 快速分配到 Star List
- 快速打本地标签
- 查看该仓库的 Star 历史趋势

**实现思路**：Content Script 在仓库页面 Star 按钮旁注入自定义按钮，点击弹出 Popover。

**优先级**：⭐⭐⭐ 高价值、低开发成本。缩短操作路径，提升日常使用频率。

---

### 5.3 搜索结果标注

在 GitHub 搜索结果页面标注已 Star 的仓库：

- 搜索结果中已 Star 的仓库显示特殊标记（如 Star 图标高亮或标签 badge）
- 帮助用户快速识别已知项目 vs 新项目

**实现思路**：Content Script 扫描搜索结果页的仓库链接，与本地缓存比对后注入标记。

**优先级**：⭐⭐ 中等价值、低开发成本。锦上添花的功能。

## 六、协作 & 分享

### 6.1 公开 Star 清单分享

把标签/分类生成一个可分享的页面：

- 生成一个静态 HTML 页面（类似 Awesome List 风格）
- 可选择要分享的标签，设置为公开或生成加密链接
- 页面包含仓库描述、Star 数、语言、标签等信息
- 支持自定义页面标题和描述

**实现思路**：客户端生成 HTML 字符串，通过 GitHub Gist 发布（类似 Remu 的 Gist 同步方案），或导出为 HTML 文件。

**优先级**：⭐⭐ 中等价值、中等成本。适合技术博主和 KOL 做"我的工具箱"分享，有传播属性。

---

### 6.2 团队共享标签配置

导出 / 导入标签分类配置，团队成员共享同一套分类体系：

- 导出为 JSON 配置文件（只含标签结构，不含 Token）
- 团队成员导入后获得相同的分类体系
- 适用于技术团队统一管理"团队推荐仓库"

**实现思路**：JSON 导出 / 导入，数据脱敏处理（不包含 Token 和个人偏好）。

**优先级**：⭐ 中等价值、低开发成本。场景较窄，适合团队使用。

---

## 七、搜索 & 筛选增强

### 7.1 高级筛选器

扩展筛选维度，覆盖更多元数据：

- **License**：MIT / Apache-2.0 / GPL / 无 License
- **最后更新时间**：最近 7 天 / 30 天 / 1 年 / 自定义范围
- **贡献者数量**：单人项目 vs 社区项目
- **Issue 状态**：有未关闭 Issue / 已解决
- **是否归档**：是 / 否
- **是否有 README**：是 / 否
- **组合筛选**：`language:rust AND license:mit AND updated:>2026-01-01`

**实现思路**：数据已在本地缓存（IndexedDB），筛选为纯客户端操作，性能无压力。

**优先级**：⭐⭐ 中等价值、中等成本。增强已有搜索功能的深度。

---

### 7.2 智能文件夹（保存的搜索）

把常用的筛选条件保存为"智能文件夹"，类似 iTunes 智能播放列表：

- 定义规则：`language == "TypeScript" && stars > 1000 && tag == "前端框架"`
- 文件夹内容随数据更新自动变化
- 支持嵌套：智能文件夹内再创建子规则

**实现思路**：规则存储在 IndexedDB，查询时在客户端执行过滤逻辑。

**优先级**：⭐⭐ 中等价值、中等成本。对重度用户（500+ Star）很有吸引力。

---

### 7.3 模糊搜索 & 语义搜索

支持更灵活的搜索方式：

- **模糊匹配**：拼写错误也能找到（如 "typscript" → "typescript"）
- **语义搜索**：输入"异步运行时"能找到 Tokio、async-std 等
- **同义词扩展**：搜索"js"同时匹配 "javascript"、"ecmascript"

**实现思路**：模糊搜索可用 Fuse.js（客户端轻量库）。语义搜索需要调用 Embedding API（如 OpenAI），成本较高，可作为高级功能。

**优先级**：⭐ 中等价值、高开发成本（语义搜索部分）。模糊搜索性价比高，语义搜索可以后期迭代。

---

## 八、通知 & 监控

### 8.1 Star 仓库 Release 动态提醒

监控你 Star 的仓库的新 Release：

- 当仓库发布新版本时，浏览器通知提醒
- 展示 Release Notes 摘要
- 支持按仓库设置"静默"（不提醒某些仓库）

**实现思路**：Background Script 定期（如每 4 小时）检查 Star 仓库的最新 Release（GraphQL `releases(last:1)`），对比上次记录的版本号。

**优先级**：⭐⭐ 高价值、中等成本。解决用户痛点中的"Star 仓库更新了但我不知道"。

---

### 8.2 仓库活跃度监控

追踪 Star 仓库的健康状态变化：

- 仓库被归档 → 通知
- 仓库 Star 数突然暴涨 → 通知（可能被推荐到首页）
- 仓库 License 变更 → 通知
- 仓库转移所有权 → 通知

**实现思路**：在增量同步时对比前后状态，检测变化并触发通知。

**优先级**：⭐ 中等价值、中等成本。功能有价值但场景较窄。

## 九、UX 体验增强

### 9.1 键盘快捷键

为高频操作设计快捷键，提升操作效率：

| 快捷键    | 功能                        |
| --------- | --------------------------- |
| `j` / `k` | 上下导航仓库列表            |
| `Enter`   | 打开仓库详情                |
| `s`       | Star / Unstar               |
| `t`       | 打开标签面板                |
| `l`       | 打开 Star List 面板         |
| `/`       | 聚焦搜索框                  |
| `Esc`     | 关闭弹层 / 退出多选         |
| `x`       | 选中 / 取消选中（多选模式） |
| `Ctrl+A`  | 全选当前列表                |
| `?`       | 显示快捷键帮助              |

**实现思路**：在 React 组件中监听 `keydown` 事件，使用自定义 Hook 管理快捷键映射。

**优先级**：⭐⭐⭐ 高价值、低开发成本。对键盘流开发者是必备功能。

---

### 9.2 多视图模式

提供不同的列表展示形式：

- **卡片视图**：当前默认，每行展示仓库卡片（名称、描述、语言、Star 数）
- **紧凑列表视图**：每行只显示仓库名 + 语言 + Star 数，一屏展示更多内容
- **看板视图**：按标签/列表分栏展示，类似 Trello 看板
- **时间线视图**：按 Star 时间分组展示，适合回顾"我什么时候 Star 了什么"

**实现思路**：视图模式存储在 `chrome.storage.local`，通过 Zustand store 管理切换逻辑。

**优先级**：⭐⭐ 中等价值、中等成本。提升不同使用场景下的体验。

---

### 9.3 多账户切换

支持多个 GitHub 账户：

- 个人账号 + 工作账号
- 一键切换，数据隔离
- 每个账号独立的 Token、标签、Star 缓存

**实现思路**：IndexedDB 以 Token 哈希为 namespace 做数据隔离，切换时重新加载对应数据。

**优先级**：⭐ 中等价值、中等成本。场景较窄（大多数用户只有一个 GitHub 账号）。

---

### 9.4 仓库对比视图

选中两个仓库并排对比：

- Star 数、Fork 数、Issue 数
- 最近更新时间、创建时间
- License、语言、依赖情况
- README 摘要

适用于技术选型场景（"我应该用 X 还是 Y"）。

**实现思路**：选中两个仓库后切换到 Split View，左右并排展示详情面板。

**优先级**：⭐ 中等价值、中等成本。场景较窄但差异化明显。

---

### 9.5 仓库备注 & 标注

为每个 Star 仓库添加私人备注：

- 记录"为什么 Star 了这个仓库"
- 支持 Markdown 格式
- 备注可搜索（搜索关键词命中备注内容时显示）

**实现思路**：备注存储在 IndexedDB，与仓库 `full_name` 关联。UI 上在仓库卡片展开详情时展示备注编辑区。

**优先级**：⭐⭐ 高价值、低开发成本。直接解决"Star 完就忘为什么收藏"的痛点。

## 十、进阶功能（长期方向）

### 10.1 AI 智能分类

利用 LLM 自动分析仓库并建议分类：

- 输入仓库的 README、topics、描述
- AI 输出建议的标签分类（如"这个仓库属于「DevOps - CI/CD」"）
- 用户确认后自动打标签

**实现思路**：调用 OpenAI / 本地模型 API，批量处理未分类仓库。可作为后台任务，用户手动触发。

**优先级**：⭐ 高价值、高开发成本。是终极差异化功能，但依赖外部 AI 服务。

---

### 10.2 依赖关系图

展示 Star 仓库之间的依赖关系：

- 哪些仓库依赖了同一个库
- 你的 Star 列表中有多少条依赖链
- 当底层依赖有重大更新时，提醒你关注上游变化

**实现思路**：解析仓库的 `package.json` / `Cargo.toml` 等依赖文件，构建依赖图。

**优先级**：⭐ 中等价值、高开发成本。功能有深度但实现复杂。

---

### 10.3 Star 清单自动生成 README

把标签/分类自动转成 GitHub 风格的 Awesome List README：

- 按标签分组，生成 Markdown
- 包含仓库描述、Star 数、链接
- 可一键发布到 GitHub Gist 或新仓库

**实现思路**：客户端 Markdown 模板引擎，根据标签数据生成文档。

**优先级**：⭐⭐ 中等价值、低开发成本。有传播属性，适合内容创作者。

## 竞品无法覆盖的空白

以上功能中，以下几点是当前竞品完全没有实现的，也是本插件的核心差异化方向：

1. **自动标签规则引擎** — 没有任何竞品支持基于规则的自动分类
2. **GitHub Star Lists + 本地标签双模式** — 竞品要么只有本地标签，要么只有 Lists
3. **GitHub 页面内标签注入** — 没有竞品在 GitHub 原生页面展示分类信息
4. **仓库健康度检测** — 没有竞品主动提醒用户"这些仓库已经死了"
5. **批量操作** — 竞品普遍不支持批量取消 Star / 移动 / 打标签
6. **SidePanel + Popup 双 UI 模式** — 竞品都是单一 Popup
